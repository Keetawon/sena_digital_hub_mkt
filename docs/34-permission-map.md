# Per-user permission map — investigation only

Snapshot: `main` at `1531b0d` (9 October 2026), after the accounts redesign. Scope: all 45 canonical migrations and the application source at this commit. This is a static, local investigation: no server/DB connections, hosted requests, real records, test runs, application changes or migrations were performed.

## Findings and scope of “exact”

Authorization is not a hierarchy. `admin` inherits an **editor** check inside `hub.require_actor`, not a publisher check. The API adds independent role checks. Several actions also depend on environment, record state, ownership, revision, vocabulary validity and agency. Navigation visibility is not an authorization boundary.

A grid of only twelve tabs × three identical bits cannot represent today's access exactly: agency binding-only edits, brand creation/request decisions, finance steward decisions, and editorial-versus-publication approval are different capabilities. Preserve these action distinctions during conversion; do not turn any partial cell below into unrestricted edit/approve. No per-tab implementation is proposed as an already approved change.

“Verified” below means traced through executable source and ordered migration definitions, including later replacements, renames and revocations. It does **not** mean a fresh runtime test or a claim about the deployed database. The local capability matrix describes callable management APIs and DB checks, even where a button is hidden. H1 availability is a separate restriction, not a grant.

The precise partial cells and exceptions:

- **Projects a:** editor/admin can confirm or reject model matching; only publisher can publish/withdraw/rollback. Publisher also has draft edit rights through API/DB (`main.writer`), although normal ProjectDetail controls allow editor/admin only. Do not backfill from visible buttons alone.
- **Brands a:** admin can resolve/reject brand requests, create brands and bulk-create; publisher publishes/withdraws/rolls back but cannot edit brands. Editor edits/request-submits but cannot create the canonical brand or resolve requests. “Manage users” must not accidentally become the authority for these unrelated admin actions.
- **Knowledge a:** editor/admin review candidate content and verify/reject expected answers; publisher approves asset rights and creates a **private preview release**. Neither role can do the other's review actions. Preview queries can record a gap even for viewer: an incidental system write, not general edit permission.
- **Registry e:** agency can submit an immutable native binding for its own registered campaign/name; cannot issue registrations, add name variants, or create scopes. Its read also filters BUD vocabulary and restricts scope visibility. Registry has no separate human approval API; corporate-label evidence is recorded as part of issuance. Admin-only DB stewardship/cancel/global approval switches exist outside the UI API.
- **Finance a:** online_staff can confirm memo records, line revisions, mappings, commitments and card batches, and save confirmed allocations; only admin can review/retire memo identifiers and corrections. `statement_create/update` can set review status. These are Hub record confirmations, not approval of the external E-memo.
- **Archive:** both roles can correct-and-confirm extraction and apply it into Hub finance records; only admin can set legal hold. That hold is an extra administrative operation, not “manage users.” There is no independent saved human draft before extraction confirmation.
- **Actuals:** view only through HTTP; operator imports are separate. **Documents/exceptions:** edit follow-up/workflow state, not source actuals or external documents. **Questions:** read-only catalog, no answer-writing API.

### Four requested confirmations

1. **Confirmed:** admin cannot publish promotions or releases. Next blocks it; FastAPI requires publisher; the SQL command/publish functions require publisher and release EXECUTE is granted only to publisher. The admin-as-editor exception does not match a publisher-only array. See [proxy route:60](../apps/admin/app/api/hub/%5B...path%5D/route.ts#L60), [main.py:368](../apps/api/sena_hub_api/main.py#L368), [M25:96](../supabase/migrations/202610020025_hosted_h1_adapters.sql#L96), [M25:158](../supabase/migrations/202610020025_hosted_h1_adapters.sql#L158), [M21:322](../supabase/migrations/202610010021_residential_demo_release.sql#L322).
2. **Agency management access to projects/brands: refuted.** The landing links remain visible, but management data is denied by FastAPI and lacks its table/function grants. This is not an assertion that agency can never see published content: the **local** proxy substitutes the service_consumer token for allowed public paths, including `/v1/projects` and `/v1/brands`; H1 forwards the user's token and its consumer dependency rejects agency. Treat this local public adapter separately from tab grants. [hub-navigation.tsx:31](../apps/admin/components/hub-navigation.tsx#L31), [proxy route:108](../apps/admin/app/api/hub/%5B...path%5D/route.ts#L108), [main.py:373](../apps/api/sena_hub_api/main.py#L373).
3. **online_staff access to promotions/releases: refuted.** No management view/edit/approve. It is not in content staff, and SQL content grants/checks exclude it. The same local public-adapter caveat applies to public projects/brands; `/v1/promotions` is not forwarded by Next. Existing negative coverage: [test_promotions.py:70](../apps/api/tests/test_promotions.py#L70).
4. **Who can answer Questions:** nobody via the Questions tab/API. Five internal roles read a versioned JSON catalog; changes go through repository maintenance, not a DB permission. Knowledge evaluation questions are different: editor/admin can save/review expected answers at `/v1/admin/knowledge/questions/{question_id}/review`. [questions.py:9](../apps/api/sena_hub_api/questions.py#L9), [questions.py:71](../apps/api/sena_hub_api/questions.py#L71), [knowledge.py:113](../apps/api/sena_hub_api/knowledge.py#L113), [M39:63](../supabase/migrations/202610070039_knowledge_followup.sql#L63).

## 7. Proposed phased design (not implemented)

### Storage and lossless conversion

Use ordinary relational rows, not a JSON blob and not JWT claims:

- `hub.user_tab_permission(account_id, tab_code, can_view, can_edit, can_approve, updated_at, updated_by)`, composite PK `(account_id, tab_code)`; FK to user_account and a server-owned tab catalog containing exactly the twelve listed tabs. Missing row means deny. Edit/approve require view; approve **does not imply edit**. Unsupported levels remain false (for example Questions edit/approve and Actuals HTTP edit).
- Keep `user_account.status` as the universal ACTIVE prerequisite. Add an independently audited `can_manage_users` flag (or equivalent protected account attribute); count ACTIVE flagged accounts for the last-admin invariant. Keep external/internal account kind and canonical agency code independent of templates, so choosing a content template never makes an agency internal.
- Templates are versioned server-owned sets of permissions copied to an account, not runtime role membership. Log template application as a permission diff. Later template edits should not silently broaden existing accounts; ask whether to propagate an explicit reviewed batch.
- Add append-only `user_permission_event` for actor, target, before/after, template version, reason and time. Admin decisions and grid writes need one lock/version check with the existing no-self/last-admin guards. Role/template changes must not manufacture a new agency or overwrite a concurrently changed grant.
- Retain an immutable **conversion snapshot of legacy action entitlements** while migrating, and an action-to-tab/level catalog in code/SQL. Partial cells need action exceptions: registry.bind_native vs registry.issue; brands.create/resolve vs brands.publish; finance.identifiers/corrections.review; archive.hold; knowledge.content.review vs knowledge.rights.approve. Administrative stewardship is not automatically covered by can_manage_users.

**Exact backfill:** derive all action entitlements from the endpoint/RPC map and grant/policy inventory, with status and agency predicates still applied at execution. For every ACTIVE account, expand its current hub_role into the matrix **plus the partial-cell action sets**. Non-ACTIVE accounts receive no effective access regardless of stored template. Preserve service_consumer and workers outside this table. Compare old vs new allow/deny for every operation/role/state before enabling a group. UI-hidden but callable publisher project edits must remain in the comparison; local public-adapter access is a separate consumer path, not an extra Projects V bit.

**The unavoidable trade-off:** with only three undifferentiated bits and no action distinctions, exact conversion is mathematically impossible. Granting “agency registry edit” as full edit broadens issuance; clearing edit breaks bindings. The recommended transition is a simple grid for the owner with explicit explanations for external accounts and a small compatibility action set under it. Before general widening, the owner must choose whether the finished product retains limited action capabilities/extra controls or intentionally normalizes these differences. Do not silently treat templates as continuing permanent authorization after the migration is advertised as complete.

### DB enforcement and trusted identity

1. Introduce a non-login, non-inheriting `hub_app` base execution role for migrated human operations. Keep public consumers, export readers, ingestion and workers separate. API DB login may SET only approved execution roles; never grant table-owner/BYPASSRLS membership or arbitrary SQL to clients.
2. Implement `hub.can(tab, level)` (and a small protected action check for the exceptions) using **the actor's ACTIVE row and permission rows from Hub**. Read actor UUID from the existing transaction GUC set only after JWT verification; ignore metadata/headers/client-supplied account IDs. Unknown actor/tab/action and missing rows deny. Avoid cached GUC permission booleans supplied by clients. Fixed search_path, bounded queries, PUBLIC EXECUTE revoked, no dynamic object names from requests.
3. The actor GUC is **a trusted API-DB-connection contract, not a cryptographic proof inside PostgreSQL**. A DB credential holder could set it today. Never expose that login to browsers/PostgREST or grant users arbitrary SQL. Direct DB tests deliberately set the GUC to simulate a verified caller; do not describe this as protection against a stolen runtime credential.
4. RLS policies call hub.can for reads; mutations use narrow, typed commands that check permissions **inside the DB before reads, locks and writes**, including every dispatcher branch. Use restricted non-bypass definer owners where necessary. A single broad SD owner with USING true will not inherit the caller's row restrictions: add explicit actor/scope checks inside those functions and/or owner policies using hub.can. SECURITY INVOKER is preferable where its required table grants cannot expose arbitrary writes; otherwise keep guarded functions and revoke direct mutations.
5. Existing FORCE RLS stays forced. Core/account/knowledge currently mostly use ENABLE RLS plus owner functions; do not claim they are already forced. Review ownership and recursion before strengthening those tables. `hub.can` needs narrowly bounded read access to account/permission tables without recursive RLS; a dedicated permission-reader owner with explicit policies is preferable to superuser/BYPASSRLS. Grant no permission-table writes to hub_app.
6. Agency isolation must be a conjunct: `ACTIVE AND external-kind AND allowed-action AND row.agency_code = account.agency_code`, plus the existing canonical/date-valid vocabulary and registered/name constraints. Do not combine a permissive general-view policy with an agency policy and expect narrowing: PostgreSQL permissive policies OR together. Use disjoint internal/external predicates or a restrictive isolation policy covering every relevant table and SD query. Test wrong/missing agency GUC against the table-backed agency, not just token text.
7. Every request rechecks ACTIVE status and effective permissions. No cross-request permission cache initially; preserve next-request suspension/role-change behavior. Long operations/streamed tools and approval transactions should revalidate at each protected step/commit. Define a transaction's snapshot semantics; never promise revocation can retract already delivered bytes.
8. Next navigation/controls and FastAPI should consume a bounded capabilities projection from /v1/me and reject early for useful errors, but SQL remains authoritative. Remove role-array checks group by group only after equivalent DB checks exist. Keep 401 versus 403 versus API-unavailable 503 distinctions and unsaved text.

### Interim narrow-only mode for groups not yet migrated

Effective access is `legacy_action_allowed AND requested_tab_bit AND action_exception_allowed AND ACTIVE AND scope_allowed`. It can only remove rights; selecting a box beyond the old role's ceiling is disabled and explained until that group is migrated. Keep legacy_hub_role frozen for this ceiling; a template selection must not secretly change it and widen an unmigrated group.

An unmigrated group must either receive DB guards for **all** its entry points/underlying reads before an untick becomes effective, or show read-only permissions and refuse to save changes for that group. A frontend/API-only “narrow” mode does not meet the owner's DB-denial requirement. Plain wrapping of one RPC is insufficient if callers retain direct SELECT or alternate SD functions. New writes to permission rows must not advertise a restriction the DB does not yet enforce.

### Later per-project / per-brand scoping (additional work only)

Would require explicit scope membership tables and inheritance rules (brand → project, project groups, historical brand reassignment), an object-aware `can(..., entity_id)` contract, dependency filtering for assets/models/promotions/release members, scoped counts/search/CSV/citations/cache keys, and rules for newly created/unassigned projects. Agency code isolation remains a separate mandatory constraint. Scope-aware locking, indexing and query plans become necessary; parent/child membership changes must revoke access consistently. This is materially larger than tab permissions and is not designed or implemented here.

### Top five risks and rough size

1. **Lossy conversion:** three bits conflate restricted actions and role-specific approval stages. A naive role-to-grid table broadens agency, finance or content approval. Mitigation: baseline action snapshot, explicit partial-cell exceptions, owner decisions before widening.
2. **Definer/ACL bypass:** changing SET ROLE alone leaves old grants, renamed functions, permissive policies and privileged function owners able to read/write. Mitigation: effective ACL audit, restricted owners, per-dispatch checks and negative SQL tests.
3. **Agency leakage:** general-view policies OR with tenant policies, vocabulary/reference joins or definer queries can bypass own-agency filtering. Mitigation: table-backed agency + mandatory isolation predicates on every path, including bindings, exports and helper RPCs.
4. **Cross-tab leakage/writes:** releases, shared assets, progress caches, RAG, assistant citations/proposals, archive→finance and exports bypass a page-based model. Mitigation: member/destination checks and safe projections; denied data must never reach a response/tool/retrieval result.
5. **Mixed-state rollout/revocation:** stale sessions/caches, legacy role checks, background role impersonation and account-admin changes can disagree. Mitigation: per-group gates, no cross-request permission cache, independent worker identities, atomic audited grid changes, no automatic fallback to old broader access.

Planning estimate, not a commitment: **12–18 migrations**, **60–90 source/test/config files**, **500–900 new or adapted parameterized permission assertions**, roughly **8–12 developer-weeks** including inventory-to-test conversion, design decisions, staged integration and regression fixes. The 203 role-sensitive objects are the audit surface, not 203 necessarily separate edits. Shared SD dispatchers and joins dominate effort. Project/brand row scoping, a writable Questions workflow and new four-eyes draft stages are additional scope. No new runtime dependency is inherently required.
